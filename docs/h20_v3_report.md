# 阶段报告：V3（GQA 共享 K/V）与 XQA 打平

## 目标

V2 把与 XQA 的差距压到 1.4–16x，并把剩余差距归因到 GQA 冗余：32 个 query head 只对应 8 个 kv head，V2 仍然让每个 query head 各自读一遍 KV，导致同一份 K/V 被读 4–8 次（`docs/h20_v2_report.md`）。V3 验证"按 kv head 复用 K/V"能否兑现这部分收益。

## V3 设计

在 V2 的 split-KV grid 与无 barrier KV 循环之上，只改一件事：**一个 block 负责共享同一 kv head 的全部 4 个 query head**。

- 契约固定 `Hq/Hkv = 32/8`，所以每个 block 覆盖 4 个 query head。
- 每个 lane 把 4 个 head 的 Q 分片全部放进寄存器（16 个 float），循环里对每个 key 只加载一次 K 分片和一次 V 分片（各 4 个 half），4 个 head 复用同一份数据。
- 每个 key 对 4 个 head 分别做 warp 归约与 online-softmax 更新；每个 head 的状态（`m, l, acc[4]`）独立保存在寄存器里。
- 每个 chunk 结束时仍是一次 barrier，把 4 个 warp 的 partial 合并；partial 布局与 V2 完全一致，因此**复用 V2 的 merge kernel**。
- launcher 新增 `max_seq_len` 参数：调用方已知最长序列时直接传入，省掉 V2 每次调用的 `seq_lens.max().item()`（一次设备 reduce + 一次 DtoH 拷贝 + 同步）。

单次调用的内存流量（`q_len=2, KV=8192, batch=1`）：V2 约 268 MB → V3 约 66.5 MB，降为 1/4。

## 正确性

`scripts/build_and_test_v3.py`：`q_len` 2/4/8 × KV 33/1024/8192，逆序 page table，chunk=128/512，并且每个配置同时验证"显式传入 `max_seq_len`"与"launcher 自动测长"两条路径。

全部通过，最大绝对误差 ≤ 4.88e-4（FP16 量级），与 `v1`/`v2` 的结果一致。

## 归因变化

| 版本 | KV=8192/q2/b1 的 p50 | 估算内存流量 | 等效带宽 | 瓶颈判断 |
|---|---:|---:|---:|---|
| V1 | 11777.5 µs | ~268 MB | ~23 GB/s | 每 key 两次 barrier，串行化 |
| V2 | 226.5 µs | ~268 MB | ~2.1 TB/s | 接近 H20 峰值带宽（约 4 TB/s 的一半） |
| V3 | 111.6 µs (chunk 512) / 82.7 µs (chunk 256) | ~66.5 MB | ~0.6 TB/s | **不再是带宽 bound** |

也就是说 GQA 复用兑现了预期的 4x 流量削减，同时也把瓶颈从内存换到了别处：每个 key 每个 lane 仍然要付 4 次 warp 归约（20 次 shuffle）和 8 次 `expf`，以及 split-KV 的 merge kernel 与启动开销。在 KV=1024 的算例上 V3 已经贴着启动/开销地板（80.8 µs vs XQA 72.1 µs），继续优化 kernel 算术的边际收益有限。

## Go / No-Go

- 目标达成：V3 在 `q_len=2, KV=8192` 上与 XQA 实质打平，在整个 12 用例子集上从 V1 的 19–203x 收敛到 **1.12–6.83x**。
- 剩余的短板集中在 `q_len=8`、`batch=4` 这类"行数多、KV 长"的算例（4–6.8x），原因是每个 query head 组仍然按行重复流式扫描 KV，而要再进一步就必须引入张量化/TMA 或按 kv head 做更激进的跨行复用——这是明显更大的工程量，且收益不确定。
- **建议在此冻结 kernel 演进**（V3 作为交付版本），把剩余精力放在交付线上：把这份可复现的评测与 harness 作为项目主体，并考虑用 36 用例数据回到 issue #3420 补一份独立测量。

## 限制

- 单卡单次采样；KV=1024 的小算例抖动明显（XQA 在 `q_len=2/KV=1024/batch=1` 上跨会话测到 45.8–72.1 µs）。
- H20 上 `ncu` 被驱动权限挡住（`ERR_NVGPUCTRPERM`），没有硬件计数器，带宽与瓶颈都是手算流量模型加时间分解的推断，不是 counter 实测。
- 计时包含 Python/launch 开销；V3 在 KV=1024 时该开销已占相当比例。
- V3 只覆盖 `q_len` 2/4/8 与 `Hq/Hkv=32/8`；`q_len=16` 未纳入自研 kernel 契约。
- 每个请求复用同一物理页集合，真实 KV cache 的页分布更分散。

## 附：V4（向量化加载）的负结果

V3 里每个 lane 拥有的维度是 `{lane, lane+32, lane+64, lane+96}`，所以每个 key 要做 4 次跨步的 2 字节加载。V4 把 lane 的维度改成连续 4 个 `[4*lane, 4*lane+4)`，K 和 V 各用两次 4 字节的 `__half2` 加载（每 lane 一次 8 字节连续访问），其余算法完全不变，用来验证"访存效率是不是瓶颈"。

正确性：与 V3 完全一致（`q_len` 2/4/8 × KV 33/1024/8192，chunk 128/512，最大绝对误差 ≤ 4.88e-4，V4 与 V3 互差 ≤ 1.5e-4）。

性能（27 用例矩阵，chunk=512）：

| 统计 | v4/v3 p50 比值 |
|---|---|
| 最小 / 平均 / 最大 | 0.95x / 0.98x / 1.01x |

**结论：只有约 2% 的提升，访存效率不是瓶颈。** V4 与 V2 的归因实验合在一起，把 V3 的瓶颈定位到了每 key 的依赖链上——每个 key 每个 lane 需要 4 次 warp 归约（20 次 shuffle）加 8 次 `__expf`，而且这些操作在 key 之间是串行的。要再往上走只能减少"每个 query 向量摊到的每 key 工作量"，标准做法是上张量化（`mma`）把归约放进硬件；那是明显更大的改造，且收益仍不确定。

因此 kernel 线仍然冻结在 V3，V4 作为"排除访存假设"的实验保留在仓库里。

复现：

```bash
python scripts/build_and_test_v3.py    # 同时校验 V3 与 V4
python scripts/run_gpu_matrix.py --variants v3 v4 \
  --q-lens 2 4 8 --kv-lens 1024 8192 32768 --batch-sizes 1 4 16 \
  --chunk-keys 512 --output results/h20_v3_v4.jsonl
```
